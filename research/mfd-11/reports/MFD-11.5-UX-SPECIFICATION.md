# MFD-11.5 UX Specification

## Document Purpose

This specification defines the interface requirements for four research-grade interfaces (A–D) to be developed under the FAHM Development Programme MFD-11.5. All requirements are derived from the UX Research Report and User Journey Map. Every proposed interface must distinguish verified, provisional, and awaiting-review data. No interface may imply AI output has scholarly approval.

---

## 1. Global Design Principles

### 1.1 Epistemic Transparency
Every piece of content displayed in any research interface MUST carry an explicit epistemic status indicator. Users must never need to guess whether content is verified, provisional, or awaiting review.

### 1.2 Non-Impersonation of Scholarly Authority
No interface element may use visual treatments traditionally associated with scholarly approval (e.g., green checkmarks, "verified" badges without qualification, seal imagery) for content that has not undergone human scholarly review.

### 1.3 Context Preservation
Research interfaces MUST maintain navigation and working-set context across page transitions. Users must be able to retrace their path and resume interrupted workflows.

### 1.4 Data Integrity Guarantee
All Quranic text, morphology data, and mapping rationales displayed in research interfaces MUST derive from pinned datasets. No runtime-generated content may appear without explicit provenance labeling.

### 1.5 Graceful Degradation
When morphology data, occurrence files, or enrichment layers are unavailable, interfaces MUST display informative fallback states rather than error messages with CLI commands.

## 2. Uncertainty Indicator System

### 2.1 Status Taxonomy

| Status Code | Label | Visual Treatment | Meaning |
|-------------|-------|-----------------|--------|
| `verified` | Verified | Green border-left + CheckCircle icon | Human-reviewed and approved by qualified scholar |
| `editorial` | Editorial | Blue border-left + BookOpen icon | Curated by editorial team; not scholarly review |
| `automated` | Automated Policy | Purple border-left + Cpu icon | Generated by deterministic policy; no human review |
| `heuristic` | Heuristic Suggestion | Dashed gray border + Sparkles icon | Algorithmically suggested; requires verification |
| `pending-review` | Pending Review | Amber border-left + Clock icon | Awaiting scholarly review |
| `rejected` | Rejected | Red border-left + XCircle icon | Reviewed and rejected; shown only for transparency |
| `unavailable` | Data Unavailable | Gray border-left + AlertCircle icon | Source data missing or incomplete |

### 2.2 Inline Badge Component

**Required Properties:**
- `status`: One of the status codes above
- `label`: Human-readable label (defaults to taxonomy label)
- `tooltip`: Expanded explanation on hover/focus
- `size`: `sm` (inline), `md` (card header), `lg` (page header)

**Behavior:**
- Badges at `sm` size render as compact pill with icon only + abbreviated label
- Badges at `md`/`lg` size render full label + optional timestamp
- Hover/focus reveals tooltip with: status definition, last review date (if applicable), reviewer/policy identifier
- Keyboard accessible: focusable with Enter/Space to pin tooltip

### 2.3 Page-Level vs. Item-Level Indicators

- **Page-level banners** remain for overall content status (e.g., "This topic is pending scholarly review")
- **Item-level badges** are REQUIRED for every ayah mapping, root→topic connection, search result association, and cross-reference entry
- When page-level and item-level statuses differ, item-level takes visual precedence within its scope

## 3. Interface A: Quranic Exploration

### 3.1 Purpose
Enable persistent, branching research threads through Quranic content with full navigation history and context preservation.

### 3.2 Core Components

#### 3.2.1 Research Thread Container
- Named thread with auto-generated UUID
- Thread metadata: creation date, last-active timestamp, item count
- Thread persists in localStorage + optional server sync
- Thread list accessible from global navigation

#### 3.2.2 Navigation Breadcrumb Trail
- Encodes full path: `[Thread Root] → [Entity Type: ID] → [Entity Type: ID]`
- Each breadcrumb node is clickable to return to that state
- Visual distinction between main path and branched explorations
- Branch points marked with fork icon

#### 3.2.3 Entity Pinning
- Any ayah, topic, root, or dimension can be pinned to active thread
- Pinned items appear in collapsible side panel
- Items retain their original epistemic status badge
- Drag-to-reorder within thread

#### 3.2.4 Thread Export
- Export formats: JSON (structured), Markdown (readable), CSV (tabular)
- Export includes: all pinned items, navigation history, annotations, timestamps
- Export metadata includes: `proposedBy: ai-assisted`, `reviewStatus: pending-scholarly-review`

### 3.3 Interaction Requirements

| Requirement | Priority | Description |
|-------------|----------|-------------|
| A-IR-01 | Must | Thread survives page reload and browser restart |
| A-IR-02 | Must | Breadcrumb trail updates on every navigation event |
| A-IR-03 | Must | Branch creation preserves parent thread state |
| A-IR-04 | Should | Thread auto-save on every pin/unpin action |
| A-IR-05 | Should | Visual diff when returning to previously visited entity |
| A-IR-06 | Could | Thread sharing via read-only URL |
| A-IR-07 | Could | Thread merge for combining parallel explorations |

### 3.4 Constraints
- Thread storage limit: 50 threads × 200 items per thread (client-side)
- Breadcrumb depth: maximum 20 levels before auto-collapse
- No modification of source data; threads are read-only overlays

## 4. Interface B: Arabic Terminology Explorer

### 4.1 Purpose
Bridge morphological data and thematic taxonomy with clear epistemic boundaries between verified linguistic facts and heuristic suggestions.

### 4.2 Core Components

#### 4.2.1 Unified Root Profile
- Header: Root Arabic form + transliteration + activation status badge
- Tab 1: Morphology (lemmas, forms, occurrences, distribution)
- Tab 2: Semantic Connections (verified + heuristic, clearly separated)
- Tab 3: Occurrences (paginated, filterable by lemma/surah/juz)

#### 4.2.2 Semantic Bridge Panel
- **Verified Connections Section**: Only root→topic mappings with human-approved linguistic rationale
  - Each connection shows: topic title, mapping type badge, rationale excerpt, reviewer ID
  - Empty state: "No verified thematic connections yet. See heuristic suggestions below."
- **Heuristic Suggestions Section**: Algorithmically generated connections
  - Each suggestion shows: topic title, dashed-border badge, confidence score, "Requires verification" label
  - Explicit disclaimer: "These are keyword-based suggestions, not scholarly classifications"

#### 4.2.3 Semantic Field Visualization
- Text-based network diagram showing related roots
- Relationship types: shared semantic domain, cognate, antonym (when verified)
- Node size = occurrence frequency; edge thickness = relationship strength
- All nodes/edges carry epistemic status badges

#### 4.2.4 Temporal Distribution Chart
- Meccan vs. Medinan occurrence counts per lemma
- Stacked bar chart with lemma breakdown
- Data derived from pinned revelation-type dataset

### 4.3 Interaction Requirements

| Requirement | Priority | Description |
|-------------|----------|-------------|
| B-IR-01 | Must | Verified and heuristic sections visually distinct with different border treatments |
| B-IR-02 | Must | Every root→topic connection carries epistemic status badge |
| B-IR-03 | Must | Lemma filter persists across tab switches |
| B-IR-04 | Should | Semantic field visualization supports keyboard navigation |
| B-IR-05 | Should | Confidence threshold slider for heuristic filtering |
| B-IR-06 | Could | Side-by-side root comparison mode |
| B-IR-07 | Could | Export root profile as structured report |

### 4.4 Constraints
- Heuristic suggestions MUST NOT use green/verified visual treatments
- Semantic field data limited to enrichment layer; no fabricated relationships
- Temporal chart only shown when revelation-type data is complete for the root

## 5. Interface C: Research Workspace

### 5.1 Purpose
Provide ephemeral, configurable working sets for comparative analysis without requiring permanent collection commits.

### 5.2 Core Components

#### 5.2.1 Workspace Container
- Named workspace with configurable layout (1-column, 2-column, 3-column, grid)
- Workspace metadata: creation date, item count, layout preset
- Multiple workspaces supported; switchable via dropdown

#### 5.2.2 Panel System
- Each panel holds one entity type: ayah, topic, root, translation edition, tafsir excerpt
- Panels are draggable/resizable within layout constraints
- Panel header shows: entity reference, epistemic status badge, remove button
- Panel body adapts to entity type (ayah card, topic summary, root profile excerpt)

#### 5.2.3 Multi-Edition Parallel View
- Add multiple translation editions to adjacent panels
- Synchronized scrolling across edition panels
- Edition metadata header: translator, language, publication year, license

#### 5.2.4 Annotation Layer
- Private notes attachable to any panel
- Notes stored locally; not visible in exports unless explicitly included
- Note indicator badge on panel header

#### 5.2.5 Structural Query Bar
- Filter workspace items by: surah range, juz, revelation type, mapping type, epistemic status
- Dynamic subsetting without removing items from workspace
- Active filters shown as removable chips

#### 5.2.6 Export & Share
- Export formats: PDF (formatted), Markdown (annotated), JSON (structured)
- Export options: include/exclude annotations, include/exclude metadata
- Share link generates read-only snapshot (requires server support)

### 5.3 Interaction Requirements

| Requirement | Priority | Description |
|-------------|----------|-------------|
| C-IR-01 | Must | Workspace state persists across page reloads |
| C-IR-02 | Must | Adding item to workspace does not navigate away from current page |
| C-IR-03 | Must | Each panel displays epistemic status of contained entity |
| C-IR-04 | Should | Drag-and-drop reordering with keyboard alternative |
| C-IR-05 | Should | Layout presets save/load per workspace |
| C-IR-06 | Should | Synchronized scroll opt-in/out per panel group |
| C-IR-07 | Could | Workspace templates for common research patterns |
| C-IR-08 | Could | Real-time collaboration (future phase) |

### 5.4 Constraints
- Maximum 20 panels per workspace
- Workspace storage limit: 10 workspaces × 50 items (client-side)
- Annotations are private by default; explicit action required to include in exports
- No AI-generated summaries or analysis within workspace

## 6. Interface D: Evidence Presentation

### 6.1 Purpose
Surface complete provenance chains inline, enabling scholars and students to assess evidence quality without deep navigation.

### 6.2 Core Components

#### 6.2.1 Inline Provenance Badge
- Compact badge on every ayah mapping, topic association, and search result
- Shows: status icon + abbreviated label (e.g., "Editorial", "Auto-Policy")
- Click/tap expands to Evidence Panel

#### 6.2.2 Evidence Panel (Slide-Out)
- Triggered by clicking provenance badge or "View Evidence" action
- Contents:
  - Mapping type + category (editorial / automated / heuristic)
  - Rationale text (full)
  - Curator/reviewer identifier (or policy version)
  - Review/approval date
  - Source dataset references
  - Related entities in evidence chain
- Panel is non-modal; user can continue browsing while panel is open
- Close button + Escape key support

#### 6.2.3 Evidence Chain Visualization
- Vertical timeline showing: Source Dataset → Processing Step → Output Entity
- Each node carries status badge
- Nodes are expandable to show intermediate data
- Chain terminates at current entity; forward links shown separately

#### 6.2.4 Review Flagging System
- "Flag for Review" button on any evidence panel
- Structured form: reason code dropdown + free-text description
- Flags stored locally until sync; visible in reviewer dashboard
- Confirmation toast after flag submission

#### 6.2.5 Evidence Dossier Export
- Generate comprehensive report for selected entity/entities
- Includes: all evidence panels, chain visualizations, flags, timestamps
- Format: PDF (formatted) or JSON (machine-readable)
- Metadata: `proposedBy: ai-assisted`, `reviewStatus: pending-scholarly-review`

### 6.3 Interaction Requirements

| Requirement | Priority | Description |
|-------------|----------|-------------|
| D-IR-01 | Must | Every searchable/indexable entity has inline provenance badge |
| D-IR-02 | Must | Evidence panel loads within 200ms (pre-fetch on hover) |
| D-IR-03 | Must | Evidence chain shows complete audit trail from source to display |
| D-IR-04 | Must | Flag submission provides immediate confirmation feedback |
| D-IR-05 | Should | Evidence panel remembers last-opened state per session |
| D-IR-06 | Should | Batch export for multiple selected entities |
| D-IR-07 | Could | Integration with external review systems via API |
| D-IR-08 | Could | Evidence comparison mode (side-by-side panels) |

### 6.4 Constraints
- Evidence panels MUST NOT fabricate missing provenance data
- When source data is unavailable, panel shows "Data Unavailable" status with explanation
- Flag reasons are predefined taxonomy; free text is supplementary only
- No automated quality scoring presented as authoritative judgment

## 7. Cross-Cutting Requirements

### 7.1 Accessibility
- All status indicators have text alternatives (not color-only)
- Evidence panels are keyboard navigable and screen-reader compatible
- Research threads support reduced-motion preferences
- Workspace layouts adapt to viewport width

### 7.2 Performance
- Inline badges render server-side; no client-side hydration delay
- Evidence panel content pre-fetched on badge hover/focus
- Workspace state serialized incrementally; no full-state saves on every action
- Thread breadcrumb updates debounced during rapid navigation

### 7.3 Internationalization
- All status labels translatable
- RTL layout support for Arabic/Urdu content in panels
- Date/time formatting follows user locale
- Epistemic terminology consistent across languages

### 7.4 Privacy & Data Handling
- Research threads stored locally by default
- Server sync requires explicit opt-in
- Annotations never transmitted without explicit export action
- No tracking of research patterns beyond session analytics

## 8. Integration Points

### 8.1 Existing Routes
All four interfaces MUST integrate with existing routes without breaking them:
- `/quran/[slug]` → Thread pinning action added to AyahCard
- `/search` → Provenance badges on results; workspace add action
- `/explore/root/[root]` → Enhanced semantic bridge panel
- `/explore/topics/[id]` → Evidence panel trigger on mapping entries
- `/ayah/[surah]/[ayah]` → Full evidence integration

### 8.2 API Dependencies
- New endpoints required:
  - `GET /api/v1/research/threads` — Thread CRUD
  - `POST /api/v1/research/flags` — Submit review flag
  - `GET /api/v1/evidence/[entityType]/[id]` — Evidence dossier
- Existing endpoints unchanged; new fields added to response schemas where needed

### 8.3 Data Sources
- All interfaces read from pinned datasets only
- No write access to `data/`, `src/`, or production files
- Client-side storage for ephemeral state (threads, workspaces, annotations)
